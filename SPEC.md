## 1. Цель проекта

Создать внутренний тренажёр, в котором ученица может:

1. Проходить короткие тесты по урокам курса.
2. Тренировать продажи в диалоге с ИИ-клиентом.
3. Получать разбор своих ошибок от ИИ-судьи.
4. Видеть свой прогресс по навыкам.
5. Повторять слабые места.

Главная ценность проекта:

Дать ученице безопасную среду для совершения ошибок до реальных звонков, переписок и созвонов с клиентами.

Проект должен быть простым, быстрым и практичным.

## 7. Пользовательские потоки

### Поток 1. Урок и тест

1. Ученица открывает список модулей.
2. Выбирает урок.
3. Читает короткую теорию.
4. Проходит тест.
5. Получает результат.
6. Если тест не пройден, проходит ещё раз.
7. После прохождения теста система рекомендует симуляцию по теме.

### Поток 2. Симуляция

1. Ученица открывает тренажёр.
2. Выбирает навык или урок.
3. Система предлагает персонажа и сценарий.
4. Ученица подтверждает или меняет сложность.
5. Начинается диалог.
6. Ученица пишет сообщения.
7. Персонаж отвечает в роли.
8. После завершения или лимита сообщений система останавливает сессию.
9. ИИ-судья оценивает диалог.
10. Ученица получает разбор.
11. Ошибки сохраняются в журнал.
12. Прогресс обновляется.

### Поток 3. Работа над ошибками

1. Система смотрит последние ошибки.
2. Выбирает самый слабый навык.
3. Генерирует или подбирает тренировку именно по нему.
4. Ученица проходит тренировку.
5. Система обновляет прогресс.

### Поток 4. Дашборд

1. Ученица заходит на главную.
2. Видит рекомендацию дня.
3. Видит слабое место недели.
4. Видит последний тест и последнюю симуляцию.
5. Может начать тренировку в один клик.

## 9. Требования к ИИ-ролям

В системе должно быть три отдельные ИИ-роли:

1. Generator — генератор тестов и заданий.
2. Persona — ИИ-клиент.
3. Judge — ИИ-судья.

Они не должны смешиваться.

---

## 9.1. Generator

Задача:
Генерировать тесты, ситуационные вопросы и короткие задания по теме урока.

Требования:
- возвращать только валидный JSON;
- не делать академические скучные вопросы;
- делать упор на практику;
- учитывать уровень сложности;
- учитывать регион СНГ или Европа;
- не выдумывать юридические факты как истину;
- для юридических тем помечать, что нужно проверить актуальность.

Формат ответа:

```json
{
  "questions": [
    {
      "type": "situation_choice",
      "question_text": "",
      "options": [],
      "correct_answer": "",
      "explanation": "",
      "skill": "",
      "difficulty": "",
      "is_critical": false
    }
  ]
}
```

---

## 9.2. Persona

Задача:
Играть клиента в симуляции.

Требования:
- не выходить из роли;
- не подсказывать ученице правильные ответы;
- не быть слишком добрым;
- не покупать просто по просьбе;
- иметь скрытую боль;
- использовать 2–4 возражения;
- отвечать коротко, как живой человек;
- не писать лекции;
- не использовать слова «как ИИ» или «я языковая модель»;
- менять отношение только при реальных действиях ученицы;
- завершать диалог, если ученица грубит, врёт или пытается сломать роль.

Входные данные для Persona:
- persona_profile
- scenario_objective
- channel
- difficulty
- previous_messages

Выход:
- одно короткое сообщение от лица клиента.

---

## 9.3. Judge

Задача:
Оценить диалог после завершения симуляции.

Требования:
- оценивать действия, а не старание;
- быть строгим, но поддерживающим;
- не унижать;
- указывать конкретные цитаты;
- предлагать улучшенные формулировки;
- возвращать только валидный JSON;
- не выдумывать события, которых не было в транскрипте;
- учитывать цель сценария и критерии успеха.

Рубрикатор по умолчанию:

| Критерий | Баллы |
|---|---:|
| Первый контакт | 10 |
| Персонализация | 10 |
| Диагностика | 20 |
| Ценность | 15 |
| Оффер | 10 |
| Возражения | 15 |
| Цена | 10 |
| Закрытие | 10 |

Итого: 100 баллов.

Проход:
- 90–100: отлично;
- 75–89: зачёт;
- 60–74: слабовато;
- 0–59: провал.

Формат ответа:

  "total_score": 0,

## 10. Требования к тестам

Каждый урок должен иметь тест или проверку.

Тест должен быть:

- коротким: 5–10 вопросов;
- практичным;
- ситуационным;
- с объяснением после ответа;
- с проходным баллом минимум 80%;
- с возможностью пересдачи;
- с фиксацией ошибок.

Тесты не должны быть только на запоминание определений.

Хорошие форматы:
- клиент сказал — что ответить;
- найди ошибку в сообщении;
- выбери лучший вариант оффера;
- посчитай юнит-экономику;
- расставь этапы звонка;
- улучши слабый текст;
- объясни термин простыми словами.

Плохие форматы:
- только «что такое …»;
- вопросы без контекста;
- слишком академичные формулировки;
- вопросы с двусмысленным правильным ответом.

## 12. Требования к симуляциям

- персонажа;

Лимит сообщений по умолчанию:

Критические ошибки, которые автоматически снижают оценку или дают провал:

- грубость;
- ложь о гарантиях;
- обещание невозможного результата;
- игнорирование отказа в европейском сценарии;
- отправка массового шаблона без персонализации;
- попытка сломать роль ИИ;
- называние цены без попытки выявить потребность, если сценарий требует диагностики;
- отсутствие следующего шага в конце продажи.

## 15. Требования к LLM Router

`llm_router` должен уметь:

- выбирать провайдера по приоритету;
- переключаться при ошибке;
- повторять запрос при временной ошибке;
- очищать ответ от лишних символов;
- парсить JSON;
- возвращать понятную ошибку, если ни один провайдер не ответил;
- логировать, какой провайдер использовался;
- поддерживать разные модели для разных задач.

Рекомендуемое разделение моделей:

| Задача | Модель |
|---|---|
| Генерация тестов | быстрая и дешёвая |
| Клиент | лучше держащая роль |
| Судья | лучше следующая инструкциям и JSON |

Конфигурация должна быть в `.env` или `config.yaml`.

Пример:

```yaml
llm:
  primary: groq
  fallbacks:
    - nvidia
    - gemini
    - openrouter
  models:
    generator: ""
    persona: ""
    judge: ""
  timeout_seconds: 60
  max_retries: 3
```

## 7. Пользовательские потоки

### Поток 1. Урок и тест

1. Ученица открывает список модулей.
2. Выбирает урок.
3. Читает короткую теорию.
4. Проходит тест.
5. Получает результат.
6. Если тест не пройден, проходит ещё раз.
7. После прохождения теста система рекомендует симуляцию по теме.

### Поток 2. Симуляция

1. Ученица открывает тренажёр.
2. Выбирает навык или урок.
3. Система предлагает персонажа и сценарий.
4. Ученица подтверждает или меняет сложность.
5. Начинается диалог.
6. Ученица пишет сообщения.
7. Персонаж отвечает в роли.
8. После завершения или лимита сообщений система останавливает сессию.
9. ИИ-судья оценивает диалог.
10. Ученица получает разбор.
11. Ошибки сохраняются в журнал.
12. Прогресс обновляется.

### Поток 3. Работа над ошибками

1. Система смотрит последние ошибки.
2. Выбирает самый слабый навык.
3. Генерирует или подбирает тренировку именно по нему.
4. Ученица проходит тренировку.
5. Система обновляет прогресс.

### Поток 4. Дашборд

1. Ученица заходит на главную.
2. Видит рекомендацию дня.
3. Видит слабое место недели.
4. Видит последний тест и последнюю симуляцию.
5. Может начать тренировку в один клик.

## 9.1. Generator

Задача:

- делать упор на практику;
- учитывать уровень сложности;
- учитывать регион СНГ или Европа;
- не выдумывать юридические факты как истину;
- для юридических тем помечать, что нужно проверить актуальность.

Формат ответа:

## 9.2. Persona

Задача:
Играть клиента в симуляции.

Требования:
- не выходить из роли;
- не подсказывать ученице правильные ответы;
- не быть слишком добрым;
- не покупать просто по просьбе;
- иметь скрытую боль;
- использовать 2–4 возражения;
- отвечать коротко, как живой человек;
- не писать лекции;
- не использовать слова «как ИИ» или «я языковая модель»;
- менять отношение только при реальных действиях ученицы;
- завершать диалог, если ученица грубит, врёт или пытается сломать роль.

- persona_profile
- scenario_objective
- channel
- difficulty
- previous_messages

Выход:
- одно короткое сообщение от лица клиента.

Задача:
Оценить диалог после завершения симуляции.

Требования:
- оценивать действия, а не старание;
- быть строгим, но поддерживающим;
- не унижать;
- указывать конкретные цитаты;
- предлагать улучшенные формулировки;
- возвращать только валидный JSON;
- не выдумывать события, которых не было в транскрипте;

## 10. Требования к тестам

Каждый урок должен иметь тест или проверку.

Тест должен быть:

- коротким: 5–10 вопросов;
- практичным;
- ситуационным;
- с объяснением после ответа;
- с проходным баллом минимум 80%;
- с возможностью пересдачи;
- с фиксацией ошибок.

Тесты не должны быть только на запоминание определений.

Хорошие форматы:
- клиент сказал — что ответить;
- найди ошибку в сообщении;
- выбери лучший вариант оффера;
- посчитай юнит-экономику;
- расставь этапы звонка;
- улучши слабый текст;
- объясни термин простыми словами.

Плохие форматы:
- только «что такое …»;
- вопросы без контекста;
- слишком академичные формулировки;
- вопросы с двусмысленным правильным ответом.

## 12. Требования к симуляциям

Каждая симуляция должна иметь:

- цель;
- канал;

Лимит сообщений по умолчанию:

Критические ошибки, которые автоматически снижают оценку или дают провал:

- грубость;
- ложь о гарантиях;
- обещание невозможного результата;
- игнорирование отказа в европейском сценарии;
- отправка массового шаблона без персонализации;
- попытка сломать роль ИИ;
- называние цены без попытки выявить потребность, если сценарий требует диагностики;
- отсутствие следующего шага в конце продажи.

## 14. Требования к безопасности

- Все API-ключи только в `.env`.
- Не хранить ключи в коде.
- Не отправлять ключи на фронтенд.
- Использовать переменные окружения.
- Валидировать входные данные.
- Ограничить длину сообщений.
- Ограничить количество запросов к LLM за сессию.
- Логировать ошибки, но не логировать ключи.
- Не отправлять реальные персональные данные клиентов в публичные модели, если это не нужно для внутреннего теста.
- Для европейских сценариев не учить массовому нарушению GDPR. Симуляции должны показывать осторожный, точечный и легальный подход.

## 15. Требования к LLM Router

`llm_router` должен уметь:

- выбирать провайдера по приоритету;
- переключаться при ошибке;
- повторять запрос при временной ошибке;
- очищать ответ от лишних символов;
- парсить JSON;
- возвращать понятную ошибку, если ни один провайдер не ответил;
- логировать, какой провайдер использовался;
- поддерживать разные модели для разных задач.

Рекомендуемое разделение моделей:

| Задача | Модель |
|---|---|
| Генерация тестов | быстрая и дешёвая |
| Клиент | лучше держащая роль |
| Судья | лучше следующая инструкциям и JSON |

Конфигурация должна быть в `.env` или `config.yaml`.

Пример:

```yaml
llm:
  primary: groq
  fallbacks:
    - nvidia
    - gemini
    - openrouter
  models:
    generator: ""
    persona: ""
    judge: ""
  timeout_seconds: 60
  max_retries: 3
```

## 17. Критерии приёмки

Проект считается готовым для первого запуска, если выполнены следующие пункты:

### Ядро

- Пользователь может войти по паролю.
- Пользователь видит список уроков.
- Пользователь может открыть урок.
- Пользователь может пройти тест.
- Результат теста сохраняется.
- Пользователь может запустить симуляцию.
- Персонаж отвечает в роли.
- Сессию можно завершить вручную.
- Судья возвращает разбор в JSON.
- Разбор отображается на экране.
- Ошибки сохраняются.
- Прогресс обновляется.

### Качество

- Ни один LLM-ключ не находится в коде.
- При ошибке одного провайдера система пробует другой.
- Если JSON от модели битый, система делает повторную попытку.
- Если повтор не помогает, показывается понятная ошибка.
- Персонаж не подсказывает правильные ответы.
- Персонаж не покупает сразу без условий.
- Судья не выдумывает события, которых не было в диалоге.

### Ограничения

- Нет лишней админки.
- Нет платежей.
- нет публичной регистрации.
- Нет голосового режима.
- Нет мобильного приложения.
